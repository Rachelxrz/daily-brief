# 工作计划书：分析师观点档案与校准系统 × 预警系统整合

版本：v1.0（2026-08-09）
本文件为执行依据，主控版本存于 GitHub（daily-brief 仓库 `docs/工作计划书.md`），归档副本存于 Drive `Analyst-Archive/system-design/`。

## 一、项目全景

三个既有组件，一条共用纪律，不新增项目：

| 组件 | 角色 | 节奏 |
|---|---|---|
| analyst-panel（观点层） | 追踪人：论断、快照、复盘、人的校准 | 天/周 |
| gate 预警系统（机制层） | 追踪体系：脆弱性、冲击、放大、后盾 | 月/季 |
| predict.py（自我校准层） | 追踪我：我的综合判断与合理化检测 | 事件驱动 |
| 共用纪律 | point-in-time、experiment registry、fidelity 命名、预登记复盘 | 贯穿 |

参考文档：《analyst-panel-项目计划》v0.2、《审计文章修订补编》R1、《整合方案》v1.0。

## 二、Claude Code 工作清单

在 daily-brief 仓库内执行；每项含验收标准。建议将本计划书与三份参考文档放入仓库 `docs/`，并在 CLAUDE.md 中声明其为项目宪法。

### Sprint 1（第 1 周）：地基
- C1. 仓库结构：建 `briefs/`、`data/`、`docs/`、`scripts/`；Actions 加"每日简报 commit 到 briefs/YYYY/MM/"
  验收：连续 3 天简报自动入库
- C2. 三个 JSONL 空文件 + `scripts/validate.py`（schema 校验，含 fidelity/model_ref 字段）
  验收：故意写坏一条记录能被 CI 拦截
- C3. gate 系统重命名：dalio_inspired_bubble、grantham_two_sigma、valuation_state + internals_state、passive_liquidity_mismatch、tail_fragility、macro_credit_gate；每个模块加 fidelity metadata
  验收：全部模块名与审计文章第一阶段清单一致，无"replication"级误标
- C4. 手工录入第一批论断（Feroli/Wilson/Struyven/高盛黄金团队），跑通"论断→JSONL→查询"
  验收：`query --analyst Feroli` 返回完整记录

### Sprint 2（第 2-3 周）：采集与快照自动化
- C5. 采集日历 cron（FOMC/CPI/非农/OPEC/EIA/财报季/周一策略周报/WGC 季度）
- C6. PDF 入库辅助：读 Drive 新 PDF → Claude API 提取论断草稿 → 人工确认入库；回填 drive_file_id
  验收：一份真实研报从上传到入库 ≤ 10 分钟人工时间
- C7. 周度快照：读 7 天简报蒸馏 snapshot，接 ALFRED 取 vintage，全字段带 available_at
  验收：任一快照可复现"当时可见数据"且无未来值泄漏
- C8. 提示行引擎：临近验证期限（默认 7 天）、分析师改口、层间新矛盾三类规则
  验收：构造测试数据三类均能触发

### Sprint 3（第 4-5 周）：机制层公开代理模块（按修订一清单）
- C9. 集中度模块：point-in-time 成分权重 → Top-5/10/20、HHI、Neff
- C10. 引用型模块：EBP（FRED）、NY Fed dealer stats（周）、H.4.1、OFR FSI、BIS credit gap（含中国）
  验收：每个模块输出带数据源、发布日、available_at 的时间序列
- C11. 状态月报模板：脆弱性各维度读数 + 面板观点分布对照 + 外部基准（OFR FSI）并排
- C12. experiment registry：`registry.jsonl` 记录每次尝试的变量/阈值/失败版本（哈希 + 时间戳）

### Sprint 4（第 6 周起，持续）：复盘闭环
- C13. 到期检查：每日扫 falsifiable_by，到期入提示行
- C14. `scripts/analyst_weights.py`：季度 Beta 后验重算 → analyst_weights.json（framework-miss 满权重、input-miss 半权重、样本 <5 封顶中性）
- C15. 年度备份：每年 1 月打包上年 briefs+data → zip 上传 Drive backup/
- C16. 决策映射表（修订二）落成 InvestOS 可读的规则配置（阈值由 Rachel 定）

## 五、存储治理规定（作为规则执行）

**规则 1 —— 按介质分家：文本与代码一律 GitHub，二进制与原始研报一律 Drive。**

| 内容 | 位置 | 保存期限 |
|---|---|---|
| 每日简报 briefs/ | GitHub | 无限期 |
| analysts / context_snapshots / reviews / registry / weights（JSONL·JSON） | GitHub `data/` | 无限期，Git 历史即审计轨迹 |
| 全部代码、workflows、CLAUDE.md | GitHub | 无限期 |
| 设计文档 md 主控版（项目计划、修订补编、整合方案、本计划书） | GitHub `docs/` | 无限期 |
| 研报 PDF 原文 | Drive `Analyst-Archive/<板块>/` | 无限期，私有 |
| 审计文章 PDF 原文及设计文档归档副本 | Drive `Analyst-Archive/system-design/` | 无限期，私有 |
| 年度备份 zip | Drive `Analyst-Archive/backup/` | 无限期 |

**规则 2 —— 主控唯一：** 所有 md 文档以 GitHub 版本为准；Drive 中的副本仅为归档，修改必须发生在 GitHub 再同步，禁止在 Drive 直接改出第二版本。

**规则 3 —— 双向链接：** PDF 只存 Drive，但每份 PDF 必须在 analysts.jsonl 或 docs 索引中有 drive_file_id 记录；反之 Drive 不存任何无 GitHub 记录指向的"孤儿文件"。

**规则 4 —— 隐私与合规：** Drive 目录保持私有，卖方研报不设任何公开分享链接；GitHub 仓库若为公开，data/ 中不得出现研报原文内容，只存自行提炼的论断与链接。

**规则 5 —— 备份方向：** GitHub → Drive 年度单向备份；Drive 的 PDF 不反向存 GitHub（体积与合规双重原因）。
